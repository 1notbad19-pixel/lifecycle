# ADR-0001: Flutter + Dart для кроссплатформенного мобильного клиента

| Поле | Значение                     |
|---|------------------------------|
| status | accepted                     |
| date | 2026-11-23                   |
| decision-makers | Зинькович Д. А. (архитектор) |
| consulted | Хута Е. В.                   |
| informed | Внук О. М.                   |

## Контекст и постановка задачи
MyPet должен работать на Android и iOS. Команда — один основной разработчик и ограниченное участие junior, срок — 6 итераций. Нужно выбрать технологию, которая даст кроссплатформенность при минимальных затратах и не потребует второй команды под iOS. Как реализовать один клиент для двух платформ без дублирования кода? Связано с SYS-NFR-001 (переносимость) и SYS-NFR-002 (запуск ≤ 2 с).

## Драйверы решения
- Кроссплатформенность (SYS-NFR-001) — доминирующий критерий.
- Скорость запуска ≤ 2 с (SYS-NFR-002).
- Ограниченные ресурсы команды (1 разработчик + junior).
- Срок проекта — 6 итераций.

## Рассмотренные варианты
1. Нативная разработка (Kotlin + Swift).
2. Flutter + Dart.
3. React Native.

## Итог решения
Выбран вариант «Flutter + Dart», потому что он единственный при одном кодовом ядре даёт приемлемую скорость запуска и не требует второй команды под iOS; затраты на освоение ниже, чем у нативной разработки.

## Последствия
- Хорошо, потому что один код на Android и iOS.
- Хорошо, потому что экосистема зрелая, есть готовые виджеты.
- Плохо, потому что размер APK/IPA выше нативного.
- Нейтрально: нужен CI под `flutter test` / `flutter build`.

## Подтверждение
CI (`flutter test`, `flutter build apk`) на каждый push; запуск на эмуляторе Android 8.0+ и проверка времени старта.

## Плюсы и минусы вариантов

**Нативная разработка (Kotlin + Swift)**
- Хорошо: максимальная производительность.
- Плохо: два кодовых ядра, двойная работа для одного разработчика.
- Плохо: не укладывается в 6 итераций.

**Flutter + Dart**
- Хорошо: один код на две платформы.
- Хорошо: скорость запуска приемлема.
- Нейтрально: больший размер сборки.
- Плохо: команде нужно освоить Dart (невелико).

**React Native**
- Хорошо: кроссплатформенность.
- Плохо: производительность таймеров и анимаций ниже.
- Плохо: сложнее интеграция звука и уведомлений для junior.

## Дополнительная информация
Связано с SYS-NFR-001, SYS-NFR-002 и представлением 012-deployment SDD. Пересмотреть, если требования к производительности ужесточатся (например, 3D-анимации).

# ADR-0002: Локальное сохранение состояния в JSON (SharedPreferences)

| Поле | Значение                     |
|---|------------------------------|
| status | accepted                     |
| date | 2026-11-23                   |
| decision-makers | Зинькович Д. А. (архитектор) |
| consulted | Хута Е. В.                   |
| informed | Внук О. М.                   |

## Контекст и постановка задачи
Прогресс питомца (имя, шкалы, монеты, улучшения, достижения, время сохранения) должен сохраняться между запусками и не теряться при аварийном закрытии. Приложение офлайн, серверной части нет. Нужно выбрать формат и место хранения. Как обеспечить надёжное сохранение и восстановление без внешней СУБД? Связано с SYS-FUNC-008, SYS-FUNC-009 и SYS-NFR-003.

## Драйверы решения
- Полная офлайн-автономность (SYS-NFR-004).
- Сохранение не реже раза в 30 с и при выходе (SYS-NFR-003).
- Простота реализации для одного разработчика.
- Целостность данных при сбое (резервная копия).

## Рассмотренные варианты
1. JSON в SharedPreferences с резервной копией `.bak`.
2. SQLite (sqflite).
3. Hive (key-value БД).

## Итог решения
Выбран вариант «JSON в SharedPreferences с резервной копией `.bak`», потому что объём данных мал (< 4 КБ), нужна минимальная сложность, а резервная копия покрывает риск повреждения файла.

## Последствия
- Хорошо, потому что нет зависимостей от СУБД и миграций.
- Хорошо, потому что легко тестировать сериализацию.
- Плохо, потому что при росте данных (история, много сущностей) JSON станет неудобным.
- Нейтрально: при смене схемы нужна версия формата и миграция.

## Подтверждение
Unit-тесты сериализации/десериализации; тест «повреждённый JSON → загрузка из `.bak`»; проверка автосохранения по таймеру.

## Плюсы и минусы вариантов

**JSON в SharedPreferences с `.bak`**
- Хорошо: минимальная сложность.
- Хорошо: достаточно для текущего объёма.
- Нейтрально: ручная миграция при изменении схемы.
- Плохо: не масштабируется на большие объёмы.

**SQLite (sqflite)**
- Хорошо: масштабируемость, транзакции.
- Плохо: избыточно для текущих данных.
- Плохо: больше кода и миграций.

**Hive**
- Хорошо: быстрый key-value.
- Плохо: дополнительная зависимость и обучение.
- Нейтрально: не даёт явной схемы без адаптеров.

## Дополнительная информация
Связано с SYS-FUNC-008, SYS-FUNC-009, SYS-NFR-003 и представлением 005-information SDD. Пересмотреть при появлении истории операций или синхронизации.

# ADR-0003: Изоляция игровой логики в domain-слое

| Поле | Значение |
|---|---|
| status | accepted |
| date | 2026-11-23 |
| decision-makers | Зинькович Д. А. (архитектор) |
| consulted | Хута Е. В.  |
| informed | Внук О. М.  |

## Контекст и постановка задачи
Игровая логика (клики, деградация шкал, экономика, болезнь питомца) должна тестироваться без запуска UI и не зависеть от Flutter. Как организовать код, чтобы логика была переносимой, тестируемой и не смешивалась с виджетами? Связано с SYS-NFR-008 (тестируемость domain).

## Драйверы решения
- Тестируемость без UI (SYS-NFR-008).
- Возможность переиспользования логики (SYS-NFR-005).
- Простота сопровождения одним разработчиком.

## Рассмотренные варианты
1. Логика внутри виджетов.
2. Логика в отдельном `domain`-слое без зависимостей от Flutter.
3. Логика в отдельном Dart-пакете.

## Итог решения
Выбран вариант «Логика в отдельном domain-слое без зависимостей от Flutter», потому что он даёт тестируемость и минимальные накладные расходы для учебного проекта.

## Последствия
- Хорошо, потому что логика тестируется чистыми unit-тестами.
- Хорошо, потому что UI можно менять без правки логики.
- Плохо, потому что нужна дисциплина импортов (проверяется архитектурным тестом).
- Нейтрально: чуть больше файлов и слоёв.

## Подтверждение
Архитектурный тест: `domain` не импортирует `package:flutter`; проверка в CI (`flutter test`).

## Плюсы и минусы вариантов

**Логика внутри виджетов**
- Хорошо: быстрый старт.
- Плохо: невозможно тестировать без UI.
- Плохо: смешение ответственностей.

**Отдельный domain-слой**
- Хорошо: тестируемость, переносимость.
- Хорошо: чёткие границы слоёв.
- Нейтрально: требует дисциплины слоёв.

**Отдельный Dart-пакет**
- Хорошо: строгая изоляция.
- Плохо: избыточно для учебного проекта.
- Нейтрально: усложняет сборку.

## Дополнительная информация
Связано с SYS-NFR-008 и представлением 004-dependency SDD.

# ADR-0004: Таймеры деградации шкал через Timer.periodic

| Поле | Значение |
|---|---|
| status | accepted |
| date | 2026-11-23 |
| decision-makers | Зинькович Д. А. (архитектор) |
| consulted | Хута Е. В.  |
| informed | Внук О. М.  |

## Контекст и постановка задачи
Шкалы питомца (голод, счастье, энергия, здоровье) должны меняться во времени, а также корректироваться за время отсутствия игрока (офлайн). Нужно выбрать механизм отсчёта игрового времени, который не вызывает гонок и прост для тестирования. Как реализовать игровое время и офлайн-деградацию без фоновых isolate? Связано с SYS-FUNC-003, SYS-FUNC-009, SYS-NFR-002.

## Драйверы решения
- Отсутствие гонок данных (SYS-NFR-002).
- Простота реализации и тестирования.
- Офлайн-деградация с лимитом 8 ч (SYS-FUNC-009).
- Совместимость с UI-потоком Flutter.

## Рассмотренные варианты
1. `Timer.periodic` в UI-isolate + расчёт офлайн-деградации при запуске.
2. Фоновый isolate с `Isolate.periodic`.
3. Серверный расчёт времени (исключён — приложение офлайн).

## Итог решения
Выбран вариант «`Timer.periodic` в UI-isolate + расчёт офлайн-деградации при запуске», потому что он исключает гонки (вся модель в одном isolate) и покрывает офлайн-сценарий без фоновых потоков.

## Последствия
- Хорошо, потому что нет блокировок и гонок.
- Хорошо, потому что легко тестировать `tick(seconds)` как чистую функцию.
- Плохо, потому что таймер останавливается, когда приложение в фоне — компенсируется офлайн-расчётом.
- Нейтрально: нужен `savedAt` в хранилище.

## Подтверждение
Unit-тесты `tick(seconds)`; тест офлайн-деградации с разными `savedAt`; проверка отсутствия импортов `dart:isolate` в `domain`.

## Плюсы и минусы вариантов

**Timer.periodic в UI-isolate + офлайн-расчёт**
- Хорошо: простота, отсутствие гонок.
- Хорошо: детерминированные тесты.
- Нейтрально: таймер не работает в фоне.
- Плохо: нужен корректный `savedAt`.

**Фоновый isolate**
- Хорошо: работает в фоне.
- Плохо: сложная синхронизация с UI.
- Плохо: избыточно для учебного проекта.

**Серверный расчёт**
- Плохо: нарушает офлайн-автономность (SYS-NFR-004).
- Плохо: требует серверной части.

## Дополнительная информация
Связано с SYS-FUNC-003, SYS-FUNC-009, SYS-NFR-002 и представлениями 008-algorithm, 010-concurrency SDD. Пересмотреть, если появятся фоновые уведомления с точным временем.

# ADR-0005: Экономика — цена улучшения ×1.15 за уровень

| Поле | Значение |
|---|---|
| status | accepted |
| date | 2026-11-23 |
| decision-makers | Зинькович Д. А. (архитектор) |
| consulted | Хута Е. В.  |
| informed | Внук О. М.  |

## Контекст и постановка задачи
Игрок покупает улучшения за монеты; цена должна расти с уровнем, чтобы прогрессия была сбалансированной и не позволяла «выкупить» всё за минуты. Нужно выбрать формулу роста цены и бонусов. Как задать экономику, которая даёт плавную, но ощутимую прогрессию? Связано с SYS-FUNC-002, SYS-FUNC-006.

## Драйверы решения
- Плавная прогрессия без «скачков» (SYS-FUNC-006).
- Простота формулы и тестируемость.
- Предсказуемость для игрока.
- Совместимость с ограниченным временем разработки.

## Рассмотренные варианты
1. Линейный рост цены (`base + k·L`).
2. Геометрический рост ×1.15 (`ceil(base · 1.15^L)`).
3. Фиксированные цены с ручным балансом.

## Итог решения
Выбран вариант «Геометрический рост ×1.15», потому что он даёт плавную, но ощутимую прогрессию и легко тестируется одной формулой.

## Последствия
- Хорошо, потому что прогрессия предсказуема и масштабируема.
- Хорошо, потому что формула проста в тестах.
- Плохо, потому что при больших уровнях цена резко растёт — нужен потолок или мягкое округление.
- Нейтрально: коэффициент 1.15 — константа, может быть вынесена в конфиг.

## Подтверждение
Unit-тесты `cost(L)` для L = 0…20; сверка с таблицей баланса; ревью значений констант.

## Плюсы и минусы вариантов

**Линейный рост**
- Хорошо: простота.
- Плохо: прогрессия быстро «выдыхается».
- Плохо: слабая мотивация покупать дальше.

**Геометрический ×1.15**
- Хорошо: плавная и ощутимая прогрессия.
- Хорошо: легко тестировать.
- Нейтрально: нужен потолок цены.
- Плохо: при больших L цена растёт быстро.

**Фиксированные цены с ручным балансом**
- Хорошо: полный контроль.
- Плохо: ручной труд, плохо масштабируется.
- Плохо: сложно поддерживать при добавлении улучшений.

## Дополнительная информация
Связано с SYS-FUNC-002, SYS-FUNC-006 и представлением 008-algorithm SDD. Пересмотреть при добавлении престиж-механик или сезонных коэффициентов.
